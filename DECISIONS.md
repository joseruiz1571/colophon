# Decisions

Only decisions made in this repository, by the operator who commissioned the build or by the builder with a stated rationale. Where the brief was ambiguous, the conservative fail-closed option was taken and is recorded here. No decision below is attributed to an operator statement that was not actually made; the operator's prompt for this build is the one page that named the product sentence, the layout, the Decision type, the demo, the controls, and the done criteria. Everything else is the builder's call.

### D1 · Greenfield layout, single package
The brief prescribes `packages/*`. Rationale: one root `package.json` with relative imports between `packages/*` directories, rather than Bun workspaces. Workspaces would add per-package manifests with no consumer yet. `$CLI` is `bun packages/cli/main.ts`.

### D2 · Autonomy level is a CSA-style L0–L5 enum
The brief says "map to CSA-style L0–L5 if easy; otherwise a documented enum". Rationale: the enum is `L0`–`L5` with each level's operational meaning in the schema description (L0 no autonomy; L1 assistive; L2 supervised, per-action approval; L3 delegated within bounds, human on the loop; L4 bounded autonomous, exception-only human; L5 fully autonomous). Both demo agents are `L3`. The mapping to any published CSA table is by intent of each level, not a citation.

### D3 · The Record is the Declaration plus provenance, and it is Cosign-signed
Rationale: the brief lists the Record's required fields; all of them live under `declaration` verbatim, and the Record adds `record_type`, `record_version`, `declaration_sha256`, `canonical_sha256`, `created_at`. Canonicalization is RFC 8785 (implemented in `packages/schema/canonical.ts` for the value space used: sorted keys, no whitespace, JSON number serialization). The gate refuses to start unless the Record's hashes recompute, its `<id>.record.sigstore.json` verifies against the presented key or identity, and record lint passes. Fail closed at bind time, not at first call.

### D4 · Data classes are labels on the call, enforced against the tool's allowed classes
Ambiguity: a gate cannot classify payload content it has not fetched. Rationale: any tool with `data_access` other than `none` must carry a `data_class` argument, and it must be one the tool is allowed to touch; an unlabeled read or write is refused (`COL-GATE-DATACLASS`, value `data_class not stated`). This makes the control honest about what it enforces: the agent's stated intent against the Declaration. The narrative and the proves table say so.

### D5 · Four rule ids on the evidence-reader, a fifth on the notifier
Rationale: the brief wants four distinct rule ids from four out-of-scope attempts. `evidence-reader` hits `COL-GATE-UNKNOWN-TOOL` (undeclared `mail.send`), `COL-GATE-SCOPE` (`admin:org` beyond `max_scopes: ["repo:read"]`), `COL-GATE-SANDBOX` (`fs.write` to `/tmp/gh-token.json` outside `out/evidence-reader/`), and `COL-GATE-DATACLASS` (`fs.read` labeled `secret` on a tool allowed `public,internal`). `notifier` hits `COL-GATE-DESTINATION` (`mail.send` to `ops@evil.example` outside `*@acme.example`). Each agent also has allowed calls that exercise the same bounds from the inside (a write inside the sandbox, an in-domain mail), so no control holds for lack of traffic.

### D6 · The one TypeScript effect is deny
The brief: verdicts come only from Rego. Rationale: `packages/gate/eval.ts` names exactly one effect, `deny` with `COL-GATE-OPA-ERROR`, when OPA cannot run, exits non-zero, returns no value, or returns a malformed verdict. That is a fail-closed safety gate, not policy. The Rego side has its own `default decision := deny` for the same reason. The probe for S11 greps for allow/deny branches keyed on tool, path, scope, or class in TypeScript and expects none.

### D7 · OPA error probe uses a policy-path override, not a broken binary
Rationale: pointing `COLOPHON_OPA_BIN` at `/bin/false` breaks record lint at startup, so the gate refuses to start and no trace exists to inspect (also fail-closed, but it does not exercise the per-call path). `COLOPHON_GATE_POLICY=/nonexistent/gate.rego` breaks only gate evaluation: every call is denied with `COL-GATE-OPA-ERROR` and the trace shows it. The startup self-test uses the same nonexistent path to record fail-closed evidence for control COL-02.

### D8 · Rego negation gotcha, recorded so it is not reintroduced
`not is_array(args.scopes)` never fires when `args.scopes` is undefined: the compiler hoists the undefined reference out of the negation and the rule body fails before `not` runs. Fixed with helper rules (`scopes_stated if is_array(args.scopes)` then `not scopes_stated`), same for `path_stated`, `dataclass_stated`, `has_to`. Found by the OPA test suite, which is why it has 34 tests.

### D9 · Cosign 3.x offline signing needs an empty signing config
Cosign 3.1.3 defaults to the new bundle format and a TUF signing config that demands a transparency log; `--tlog-upload=false` is rejected, and so is the legacy `.sig` route without a signing config. Rationale: `cosign signing-config create --no-default-fulcio --no-default-oidc --no-default-rekor --no-default-tsa` yields a config with no services; `sign-blob --key --bundle --signing-config` then signs offline and writes a Cosign 3 bundle (`application/vnd.dev.sigstore.bundle...`). Verification of a key-mode bundle needs `--insecure-ignore-tlog` because there is no log entry to check; the README says so. Keyless in CI uses the default public instance with no such flag. Probed in a scratch directory before any code was written: sign exit 0, verify exit 0, tampered blob verify exit 1.

### D10 · OSCAL 1.2.3, vendored, validated with ajv in draft-07 mode
The brief says "Prefer 1.1.2 if 1.2 schemas are painful". Rationale: the NIST 1.2.3 JSON schema is draft-07 and compiles under ajv with `strict: false`; a minimal document validated in a scratch probe, so the newest release is used and vendored at `packages/report/vendor/`. The AR carries one finding per control, one observation per cited evidence item, and back-matter resources whose `rlinks` point at bundle-relative paths with SHA-256 hashes of the file bytes. `import-ap` points at the shipped catalog resource, since Colophon has no separate assessment plan.

### D11 · Verify-phase controls get a second AR, outside the bundle
Ambiguity: "manifest completeness evaluated after the bundle exists" and "signature present" cannot be findings inside a document that is itself covered by the manifest and the signature. Rationale: the catalog marks COL-08 and COL-09 `phase: verify`; the in-bundle AR covers the eight assess-phase controls; `colophon bundle verify --out <dir>` writes `verification-results.json` (same schema, same builder) with those two findings, plus evidence items for the manifest and signature files. A bundle does not attest to its own signature.

### D12 · Unexercised controls are not-satisfied, never vacuous
Rationale: a session with zero refusals cannot show that refusals carry rule ids. COL-03 reports `not-satisfied` with the rationale "not exercised" in that case, and the narrative says the same. Likewise a foreign PEP with no Record gets `not-satisfied` on the Record-dependent controls with the reason stated; the claude-hook and aws-config packets show 5/8 for exactly this reason. This is what "their gate, your packet" honestly looks like. The agentcore-dogwood demo packet *does* bind a Record (`red-team-coder`) so the sealed directory is a signed RoE artifact; COL-02 (Colophon gate self-test) remains not-satisfied because Dogwood, not `gate.rego`, is the PEP.

### D13 · Executed-within-Record is checked by re-evaluating through the policy
Rationale: control COL-05 re-runs every allowed decision's redacted arguments through `gate.rego` and expects allow again; the breach fixture (a sandbox escape recorded as allowed) turns it not-satisfied. This keeps assessment logic out of TypeScript conditionals and reuses the one policy. Redacted arguments keep paths, scopes, destinations, and labels; secret-shaped values become `sha256:<hex>` commitments, which no rule keys on.

### D14 · Demo key pair is generated per run under `out/`, with a fixed non-secret password
Rationale: the local demo needs a key; generating one per run under the gitignored `out/` directory keeps keys out of the tree. `COSIGN_PASSWORD` is the literal `colophon-demo`, which protects nothing and is not meant to. `.gitleaks.toml` allowlists `out/` and the scenario file that carries the synthetic `FAKE-DEMO-CREDENTIAL` value used to prove redaction; the value is deliberately shaped unlike any real token, and the test that exercises value-shaped redaction builds its sample at runtime, so no committed literal matches a credential scanner.

### D15 · Probe runner clones committed HEAD
Rationale: the brief says a claim is done only when its probe ran from a fresh clone. `tests/probes.ts` clones the repository's committed HEAD into a temp directory, installs with `--frozen-lockfile`, runs the demo, then runs every SPEC probe there and writes `out/probes.json`. Uncommitted work is invisible to it by design. STATUS rows are written from that output and cite the HEAD they ran at.

### D16 · Repository pushed only on the operator's word
Rationale: creating a public remote is outward-facing, so the builder stopped before it and asked. The operator said "push it" on 2026-09-10; the repository is `github.com/joseruiz1571/colophon` and the first CI run (34505148818) was green, including keyless Sigstore signing and pinned-identity verification. Until that run, STATUS marked S37 partial.

### D17 · Installed nothing
Bun 1.4.0, OPA 1.19.1, Cosign 3.1.3, jq 1.8.2, and gitleaks 8.30.1 were already present on the build machine; CI pins the same Bun, OPA, and Cosign versions and installs gitleaks at the same version.

### D18 · Second look: destination must be exactly one key
An independent read-only review (in-family, non-forked) found that `destination_of` preferred `to` over `url` for every tool, so a fetch could pass the destination check on `to` while the upstream fetched `url`. Rationale: a call to a destination-bound tool now needs exactly one of `to`/`url`; none or both is refused with `COL-GATE-DESTINATION` (value `ambiguous destination: [...]`). Regression tests added.

### D19 · Sandbox write paths are directories, and non-string scopes are refused
Same review: `write_paths: ["out/notifier"]` admitted `out/notifier-evil/x` under a bare `startswith`. Rationale: the policy normalizes every prefix to end in `/` (`dir_prefix`), and record lint additionally refuses a write path without a trailing slash (`COL-REC-SANDBOX-SLASH`). A `scopes` array carrying a non-string entry is refused rather than ignored.

### D20 · Trace head commitment, rewritten after every decision
Same review: a chain with no terminal commitment verifies after its last N lines are removed. Rationale: `TraceWriter` rewrites `<trace>.head.json` (line count, last hash) after every append; `verifyTrace` checks it and reports `sealed`; the packet builder refuses a trace without one; a writer refuses to resume a trace that does not verify. The head is written by the same process as the trace and covered by the bundle manifest, so it is a commitment against post-hoc truncation, not against a hostile writer — the proves table already says the packet proves what the PEP recorded, not that everything passed through it. First attempt sealed on transport close, which never ran because the MCP client transport SIGTERMs the child on close; the running commitment needs no close hook.

### D21 · Redaction never truncates policy-bearing keys
Same review: an 80-character truncation with a `...` marker made a compliant long path re-evaluate as a traversal. Rationale: `path`, `to`, `url`, `scopes`, `data_class`, `repo`, `org` are never truncated; other strings are clipped at 200 characters with a `[+N chars]` marker that contains no dots.

### D22 · Two probes rewritten because they passed vacuously
Same review: the S11 grep excluded any line containing `effect`, so a hard-coded verdict passed it; the S19 probe broke cosign at `version`, so the sign failure happened before any packet existed. Rationale: S11 is now `tests/no-ts-verdicts.ts`, which flags any effect literal outside the one fail-closed deny and the adapters' translation of a foreign verdict field (it catches a planted `if (name === "mail.send") return { effect: "deny" }`); S19 uses `tests/fake-cosign-signfail.sh`, which passes every cosign command except signing a bundle manifest, so records sign, the session runs, the bundle is created, and only then does signing fail — the probe asserts the bundle and trace exist, no `manifest.sigstore.json` does, and no `SIGNATURE:` line was printed.

### D23 · Second look, findings 7–13, adopted
Glob destinations now match with null delimiters so `*` crosses dots and slashes (`first.last@acme.example`, nested URL paths); the schema wording "glob on address, host, or URL prefix" is now true. Record lint refuses a tool named `*.write`/`.delete`/`.put`/`.create` that declares a non-write `data_access` (`COL-REC-ACCESS-MISMATCH`), since the sandbox rule keys on the declared access. The gate's prefix conventions (`auth.`, `mail.`, `net.`) remain a documented limit: a tool named outside them is bound only by what its Record entry declares (`destinations`, `data_classes`); an explicit capability field is future work, not claimed. `record verify` exits 1 without `--pubkey` unless `--hash-only` is stated. `bundle sign` prints `written:`; only `bundle verify` and the demo (after verify) print `SIGNATURE:`. `bundle verify` now re-verifies every bundled Record's hashes and signature with the presented key or identity and checks that every gate decision's `record_sha256` is a verified bundled Record. The S28 probe now also removes a file. The `[REDACTED]` wording in the schema and D13 was stale after ad5f207 and is corrected.

### D24 · History rewritten once, before the first push, to remove a token-shaped literal
The private push gate on this machine refuses any public destination whose history contains a string shaped like a real credential, and the synthetic `ghp_FAKE…` value in the scenario and one test matched. Rationale: the repository had never been pushed, so history was rewritten in place (`git filter-branch`, every commit, both files; a full bundle backup was taken first) and the literal replaced with `FAKE-DEMO-CREDENTIAL-do-not-use-0000`, which no scanner mistakes for a token. Commit hashes cited above were remapped to the rewritten ones. The rule going forward: a fixture credential must never be shaped like a real one; the redaction-by-value test builds its sample at runtime.

### D25 · AgentCore Gateway + Dogwood is a foreign PEP, fixture-first
Ambiguity: AWS Bedrock AgentCore Gateway + Dogwood (Cedar-compatible, temporal) is a real PEP for agent tool calls. Colophon could have re-encoded those policies in `gate.rego`, or shipped a live CloudWatch/EventBridge collector in the same change as the adapter. Rationale: Colophon is custody, not a rival PEP. The new adapter `packages/adapters/agentcore-dogwood` only translates recorded allow/deny (and fail-closes missing/unknown to deny, `AGENTCORE-NO-DECISION`). It does not evaluate Dogwood. `packages/adapters/aws-config` stays CloudTrail/IAM infrastructure PEP evidence and is not the AgentCore path. Declaration `pep` is optional and, when present, must name `kind` and `enforcement_mode` (`ENFORCE` vs `LOG_ONLY`); the demo Record also names tool schema ref, policy set id/version/hash, engine id, and Gateway id. LOG_ONLY decisions are stored as evaluated, with the mode in reasons — Colophon does not pretend they were enforced. Phase 4 live ingest is deferred in writing: no AWS SDK, no credentials, no network in tests, demo, or CI beyond the existing Sigstore keyless job. The demo fixture is an AI red-team / coding-agent RoE trace (in-scope allow, approve-before-act deny then allow, out-of-scope deny, rate-limit deny) so the packet is scope evidence, not a happy path. CLI naming follows `colophon normalize <adapter>` (`agentcore-dogwood`), not a new `ingest` verb.

### D26 · Finding export is club interop, not a collector and not a pivot
Ambiguity: GRC Eng Club `finding.schema.json` v1 is a resource-evaluation contract aimed at CloudTrail-style inspectors (`aws_s3_bucket`, SCF control ids). Colophon could have dual-emitted CloudTrail, replaced `controls.yaml` with SCF, or treated Finding JSON as the product. Rationale: Colophon stays an agentic receipt. `packages/export/finding` is an output speaker on the Decision stream. Resource type is `ai_agent_session` (session_id, PEP source in tags/`pep_source`); evaluations use Colophon ids (`COL-*`, `COL-GATE-*`, or the PEP-native rule id). Catalog `satisfied`/`not-satisfied` map to `pass`/`fail`. Decision effects map as PEP verdict polarity: `allow`→`pass`, `deny`→`fail`, `escalate`→`inconclusive` — a deny is a recorded refusal, not a silent claim that a catalog control is unmet. No SCF control IDs are emitted; a stub crosswalk lives in `packages/export/finding/README.md`. The schema is vendored unchanged and validated with Ajv 2020-12 (`strictRequired` off: the club `if/then` requires `message`/`severity` on fail without repeating those property defs in `then`). Findings are written beside the packet (`findings/`), never into the Cosign bundle. CloudTrail dual-emit remains deferred (`aws-config` is still the infrastructure-PEP fixture). Empty input fails closed with `inconclusive` `COL-04` rather than a vacuous pass. CLI verb is `colophon export finding`, consistent with `report` / `normalize`.

### D27 · Phase 4 is captured APPLICATION_LOGS ingest, not a CloudWatch collector
Ambiguity: "live" AgentCore ingest could mean an AWS SDK pull from CloudWatch/EventBridge, or an offline reader for Gateway APPLICATION_LOGS that were captured elsewhere. Rationale: Colophon remains custody. The adapter now accepts APPLICATION_LOGS JSONL (AWS `{key=value}` requestBody, not strict JSON) and joins `Started processing request` to `Policy evaluation completed` / `Policy evaluation denied request` on `request_id`. Session id is not in the log body — AgentCore Gateway does not write it there — so it is required from a sidecar `<stem>.meta.json` or `--session`; missing both fails closed. Empty `determiningPolicies` maps to `AGENTCORE-DEFAULT-DENY` (distinct from AuthorizeAction `AGENTCORE-IMPLICIT-DENY` / missing-decision `AGENTCORE-NO-DECISION`). The vendored fixture is the operator's real ENFORCE + AWS_IAM RoE session (`7461903f-…`, Gateway `colophon-roe-gateway-dwg0z4emza`; account id redacted, principal name generalized per D28). CLI keeps the existing `normalize agentcore-dogwood` verb. Still no AWS SDK, no credentials, no network in tests, demo, or CI beyond Sigstore keyless. A CloudWatch collector is not claimed.

### D28 · Identity cues in the live capture are generalized, the capture is otherwise byte-identical
Three outside evaluations (a pre-show evaluation, a substance assessment, and a hygiene audit, 2026-09-15) read the repository cold. Two flagged that the live APPLICATION_LOGS fixture named an IAM user and carried the account's last four digits while SPEC §2 says fixture names are synthetic. Rationale: the IAM principal in the log lines, the Declaration owner, and the kill-switch text now say `roe-operator`; `account_last4` is dropped from the sidecar; request ids, trace ids, policy ids, Gateway and engine ids, timestamps, and the allow/deny sequence are untouched, so every S40 assertion still holds. SPEC §2 now says the one live capture is real with the account redacted and the principal generalized, which is the true posture.

### D29 · Reasons carry a role; only binding reasons are bounds; foreign-PEP COL-05 maps tool names and says what it checked
Same evaluations, two defects on the flagship live packet. First, COL-05 reported all three allowed calls outside the Record because the Gateway records tools as `StatusTarget___get_status` and the Declaration names `get_status`; a reader saw a scope breach where there was a naming projection. Second, the narrative rendered every reason as "Bound by X; the value fell outside it", so `request_id` and the principal ARN read as bounds. Rationale: `Reason.role` is `binding` (default), `explanation` (the PEP's own text), or `context` (provenance). Every adapter tags its reasons; the narrative quotes explanations verbatim, renders only binding reasons as bounds, and lists context in parentheses; COL-03 counts binding fields. The Record's optional `pep.tool_name_prefix` names the projection, and COL-05 strips it before re-evaluation. COL-05's rationale for a foreign PEP now says it is declaration consistency through `gate.rego`, not a re-run of Dogwood or Cedar; the alternative, reporting COL-05 as not evaluable for foreign PEPs, would have thrown away a real check (the declared tools were the tools that ran) to avoid a wording risk.

### D30 · Redaction commits substrings with the pattern COL-10 scans for, at every seal, and a COL-10 failure refuses to sign
Same evaluations, reproduced here: a `ghp_` token embedded in a Bash command was sealed verbatim into a trace, both in `args_redacted` (the old value rule matched only a whole string's prefix) and in `reasons` (the adapter quoted the raw command). COL-10 flagged it and the packet signed anyway, which contradicted SPEC §2. Rationale: one `CREDENTIAL_PATTERN` lives in `normalize/decision.ts` and both redaction and COL-10 use it, so "redacted" and "checked" cannot drift; `redactString` commits every match inside a string and the surrounding text survives (a command keeps its shape); a PEM header anywhere commits the whole string; adapters redact before they truncate; `sealDecision` redacts every string reason value regardless of adapter, so a new adapter cannot reintroduce the class; COL-10 scans reasons as well as arguments; and `buildPacket` throws before `bundle create` when COL-10 is not-satisfied, removing the staged copy. Known limit, stated rather than fixed: commitments are unsalted SHA-256 of the value, which is fine for high-entropy tokens and a dictionary target for a weak password; keyed commitments are future work.

### D31 · Packets carry relative paths; hygiene and surface changes from the same round
Rationale, one line each. Paths in a packet (task text, verify command, sidecar reference) are relative to the directory it was built from, because a portable receipt must read the same on every machine (S43). SPEC says Bun ≥ 1.4 because `bun.lock` is lockfile version 2; an evaluator's Bun 1.3.13 failed `--frozen-lockfile` with "Unknown lockfile version". GitHub Actions are pinned to commit SHAs resolved from the GitHub API, which an attestation showcase should have had from the start. `SECURITY.md`, `CONTRIBUTING.md`, `SHOW.md`, and `docs/walkthrough.md` exist; `.gitignore` covers env files and key material; the README carries a CI badge, a diagram, a positioning section with a crosswalk to the IETF decision-receipt draft, and a section that owns the agent-built method. A private audience's name is out of the README. The "the brief" wording in this file stays: the introduction scopes exactly what the commissioning prompt named, and rewriting the record to hide that would be less honest, not more. `package.json` stays `private` with the reason stated in the README. Not done here, on purpose: a `colophon hook` PreToolUse PEP, a second (PEP-side) signature, the `colophon.dev` namespace, and reconciling the Declaration with the Governance Card Stack are design decisions for the operator, not cleanup.

### D32 · Colophon for Claude Code: the gate's verdict path over a PreToolUse hook, sealed at session end
Ambiguity: the strongest MVP named by the outside evaluations was "the whole loop on a reviewer's laptop with a tool they already use", and the claude-hook adapter was fixture-only (nothing produced the log). Colophon could have wrapped Claude Code's MCP servers with the reference gate, or read Claude Code's transcript after the fact. Rationale: `colophon hook` is a Claude Code PreToolUse hook, one process per tool call, that binds the Record, decides through `gate.rego` via the same `decide()` the gate uses, appends one chained Decision, and answers `allow` / `deny` / `ask` (for `escalate`); `colophon seal` turns the trace into a packet with source `colophon-hook`. The verdict path is unchanged, so S11 still holds: the hook's only effect literal is the translation into Claude Code's permission vocabulary, and the fail-closed deny now lives in one function (`failClosedDeny`) shared by gate and hook. Naming: Claude tool names are projected onto declared names by a fixed table (`Write` → `fs.write`, `Bash` → `shell.exec`, `mcp__s__t` → `mcp.s.t`), the same kind of naming contract as `pep.tool_name_prefix` (D29); the Decision's `tool` is the declared name so COL-05 re-evaluation is exact, and the Claude tool name plus a hash of the full input ride as context reasons. Paths inside the session's working directory are relativized before the sandbox rule so a Record's `write_paths` is written once and signed for any machine; paths outside stay absolute. Labels: Claude Code never sends `data_class`, so a new optional Declaration field `defaults.data_class` fills it, recorded on the Decision as the operator's label, not the agent's (D4 stays honest; the Declaration's `pep` block was not reused because there Colophon is the PEP). Cost: about half a second per call (eight calls in 3.7 s: process start-up, cosign verify, OPA lint, OPA decide), accepted for v1 over a cached bind; a cache is a second place trust could hide. Limits stated in `docs/claude-code.md`: the hook records that the human was asked, not what the human chose; a disabled hook records nothing. Not exercised inside a live Claude Code session from the build machine, which cannot nest a `claude` process; the demo's seventh packet comes through the real `hook` command one process per event, and STATUS says so.

### D33 · The policy text is in the packet: `policy_sha256` on Colophon verdicts, `pep.policies` on foreign Records, staged under `policy/`, asserted by `bundle verify`
Ambiguity: a packet bound every decision to a signed Record (`record_sha256`) and nothing to the policy that decided it, so S9 was the exploit written as a feature: one edited line of `gate.rego` flips a deny to an allow and the packet still verifies. On the live AgentCore packet the Record named a policy set id and an engine id with no hash, and both refusals cite `AGENTCORE-DEFAULT-DENY`, so "each refusal cites a rule" meant the implicit one. Colophon could have required the field on every Decision, re-evaluated verdicts against the bundled policy at verify time, or hashed AWS's raw `get-policy` responses. Rationale, one decision each. `policy_sha256` is optional on the Decision, exactly as `record_sha256` is: foreign adapters emit Decisions without it, and the OPA-error path (whose deny already names the missing policy) omits it rather than hashing nothing. The hash is over the raw bytes of `gate.rego`, taken per call and never cached, because the manifest hashes bytes and equality with the manifest entry is the whole check. The gate and the hook stamp it; the packet builder stages `policy/gate.rego`, refuses to sign when any decision's hash differs from the staged file (the same shape as the COL-10 refusal: no bundle, no stage), and `bundle verify` reports the binding on its own `policy:` line so a swapped policy fails on the binding and not only on the manifest. For a foreign PEP the binding lives on the Record: `pep.policies[] {id, kind, path, sha256}` names each policy the engine held, its statement file is staged as `policy/<id>.cedar`, and `bundle verify` asserts each declared hash; the live `colophon-roe` Record declares the two Cedar permits and the Dogwood temporal permit that produced the capture. Those statement files are the `get-policy` statements with the account id masked (`****`) and the IAM principal generalized to `roe-operator`, the D28 rule applied to policy text as it is to the log lines; the hash is over the redacted bytes and the narrative says so, and the operator reproduces it by applying the same two substitutions to the `get-policy` output. Raw `get-policy` files were never piped into the repository. New control COL-11 (`policy-bound`) reports the binding in the catalog, because a binding that is not a control reaches neither the OSCAL AR nor the Finding export: satisfied on the two gate packets, the hook packet, and the live AgentCore packet; not-satisfied with the reason on claude-hook, aws-config, and the AuthorizeAction fixture (its Record declares no policies), which is the honest shape and the reason S46's count moved from 8/8 to 9/9. COL-11's foreign branch also requires every allow decision's rule ids to be declared policy ids, so a permit the packet cannot show the text of is a finding. Deferred, stated in the narrative: verify-time re-evaluation of COL-05 against the bundled policy; `bundle verify` never re-runs assess controls, the AR carries the build-time result, and the hash binding makes that result attributable to a policy text the stranger can read. Not claimed: that the redacted statement is byte-identical to what AWS enforced (it is not; two substitutions were applied), or that binding the permits changes which rule the refusals cite (it does not; it shows the permits that did not match). Prompted by BUI-96 (filed 2026-09-11), the Proof-of-Control claim set's required `policy_bundle_hash` ("a verdict that cannot be re-derived is not evidence"), and a Distinguished Review Board member naming policy binding as a top-two buyer ask at the 2026-09-23 launch.
